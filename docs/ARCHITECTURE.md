# Architecture

How AutoClick 2.x is put together, and why. Decisions that are easy to question later are recorded at the end.

## Projects

```text
AutoClick.Core       net10.0                     models, settings and file formats (+ 1.x migration),
                                                  scheduling, hotkey parsing, DPI math. No Windows APIs.
AutoClick.Win32      net10.0-windows10.0.19041   Win32 interop generated by CsWin32: input, windows,
     │                                            pixels, DPI scopes, hotkeys, WinEvent hooks, elevation
     ▼
AutoClick.Services   net10.0-windows10.0.19041   click engine, settings/profile/session stores,
     (depends on Core only)                       scheduler, updates (Velopack), log buffer
     ▼
AutoClick.UI         net10.0-windows10.0.19041   WPF + WPF-UI, MVVM (CommunityToolkit), overlays, tray,
                                                  localization, Generic Host composition root
```

`AutoClick.Win32` and `AutoClick.Services` both depend only on Core; the UI composes them. Core defines the platform abstractions (`IInputSender`, `IWindowInspector`, `IPixelReader`, `IElevationService`) that Win32 implements and the engine consumes, so the engine is tested with fakes. Architecture tests check the project references, the compiled references, and that view models never reference views or overlays.

## Startup

`Program.Main` (the WPF `App` is a plain page, so startup order is explicit):

1. `VelopackApp.Build().Run()`: install/update/uninstall hooks run here and exit.
2. Logging (Serilog: daily files, an in-app buffer) and settings, including the one-time migration from 1.x.
3. If *Always run as administrator* is on and the process is not elevated, relaunch with `runas` (arguments passed on the command line, `--restarting` added). A cancelled UAC prompt continues without elevation instead of looping.
4. Single instance: a named mutex and a named pipe, both with an ACL for the current user. A second launch asks the first one to show its window and exits.
5. Generic Host with dependency injection (`ValidateOnBuild`), then `App.Run()`.

`--smoke-test` skips 3-4, uses `%TEMP%\AutoClick-smoke` as data folder, applies the theme before showing the window as a normal start does, opens every page in every theme and language plus the dialogs and a heatmap, checks that page text and chart text follow the theme, and exits 1 on any binding error or wrong text color.

## Click engine

`ClickEngine` starts one `ClickSession` per game (at most one per id). A session is an async loop:

- Run every step in order (click or key press with `PostMessage`, the configured delay between steps), then wait for the interval (fixed or random). Time comes from `TimeProvider`, so tests run on fake time.
- Pause and resume use an async gate; stop cancels the loop and waits for it.
- Every coordinate conversion runs in a `DpiScope` for the game window (`SetThreadDpiAwarenessContext` with the window's own awareness), so points stay correct for DPI-unaware games on scaled monitors. Clicks get a small jitter, clamped to the client area.
- `PostMessage` results are interpreted: access denied (5) means the game runs elevated (UIPI) and stops with *ElevationRequired*; an invalid window (1400) stops with *WindowClosed*; a full message queue (1816) and other errors are retried, and five failures in a row stop the session (*TargetNotResponding* or *Error*). Blocked or failed sends are never counted as clicks.
- A minimized game is not out of bounds: the session waits until it is restored.
- The pixel color guard reads the pixel (`GetPixel`, falling back to `PrintWindow`) and skips, stops, or waits with a timeout; mismatch logging is rate limited.
- Statistics are lock-free counters plus a heatmap dictionary with a version number, so readers redraw only when something changed.

## Persistence

| Data | File | Format |
|------|------|--------|
| Settings | `settings.v2.json` | Schema 2, enums as names, `Normalize()` on load. Written atomically (temp file, flush, move). An unreadable file is moved aside and reported. |
| 1.x settings | `settings.json` | Read once to migrate; never written, so 1.x keeps working after a downgrade. Backed up to `backup\settings.v1.json`. |
| Profiles | `profiles\{id}.json` | The 1.x layout (property names, enums as numbers). Ids must match `^[a-z0-9]{8,32}$`; the file name is the id that counts. |
| Sessions | `*.autoclick-session` | Schema 2 (settings, profiles, saved games); schema 1 files still import. |

Everything lives in `%LocalAppData%\AutoClick`, which is also Velopack's install folder: uninstalling removes the data.

## User interface

- **Shell:** WPF-UI `FluentWindow` with a title bar row, a `NavigationView` (Queue, Dashboard, Settings, About), info bars for app-wide notices, a `ContentDialogHost` and a snackbar presenter. Pages and view models are singletons from the container. Each page sets its own themed `Foreground`, because WPF-UI's implicit `Page` style does not apply to page subclasses.
- **MVVM:** CommunityToolkit.Mvvm source generators (`[ObservableProperty]` partial properties, `[RelayCommand]`). View models use services; dialogs and file pickers go through `DialogService`.
- **One clock:** `UiTicker` raises a single once-per-second tick for statistics, the scheduler, window checks and the dashboard (1.x had five timers).
- **Localization:** `LocalizationService` reads `Strings*.resx`. XAML binds through `{l:Loc Key}` (an indexer binding), so changing the language updates the whole UI without a restart.
- **Overlays:** the coordinate picker is placed over the game's client area in physical pixels (`SetWindowPos`), so it works on any monitor. The heatmap is a click-through, no-activate, tool window that follows the game through out-of-process WinEvent hooks (focus and location, filtered by process and window, at most one update per frame) with a one-second fallback, shows only while the game or its dialogs are in front, and draws all markers in one `OnRender` pass with frozen brushes.
- **Hotkeys:** registered on a message-only window owned by the UI thread; registration results are reported; recording a new hotkey suspends the old ones and re-registers them in a `finally`.

## Updates

Velopack (`packId` `AutoClick`, channel `win`, main exe `AutoClick.UI.exe`, none of which may change) reads this repository's GitHub Releases. `UpdateService` checks at startup and every six hours when enabled, downloads in the background, and either restarts into the update (after stopping sessions, saving settings, flushing logs and releasing the single-instance lock) or applies it on exit.

## Build, tests and CI

- One version in `Directory.Build.props`; packages in `Directory.Packages.props` (central package management with transitive pinning); tools in `.config/dotnet-tools.json`.
- Tests: xUnit v3 on Microsoft.Testing.Platform. Core and Services tests use fixtures from real 1.x files and fake time; Win32 tests drive real windows in-process; architecture tests cover layering and localization.
- CI gates and the release pipeline are described in [CONTRIBUTING.md](../CONTRIBUTING.md) and [RELEASING.md](RELEASING.md).

## Decision records

### 1. Stay on C# and .NET 10 (October 2026)

**Considered:** rewriting the engine in C++ or Rust, or the whole app in another stack.
**Decided:** keep C#, move from .NET 8 (end of support November 2026) to .NET 10 LTS.
**Why:** the engine sends a few window messages per second; a P/Invoke call costs microseconds, so a native engine gains nothing measurable while adding an FFI boundary, a second toolchain and more antivirus false positives. The real problems of 1.x were correctness bugs, which a rewrite in place fixes.

### 2. WPF with WPF-UI (October 2026)

**Considered:** WinUI 3, Avalonia, WPF's built-in Fluent theme, WPF-UI.
**Decided:** WPF with [WPF-UI](https://github.com/lepoco/wpfui) 4.x.
**Why:** WPF-UI gives a complete Fluent control set (navigation, content dialogs, info bars, number boxes, theme following Windows) on top of the existing WPF code, overlays and LiveCharts2. WinUI 3 complicates transparent click-through overlays and unpackaged deployment; Avalonia would mean rewriting every view and overlay for no user-visible gain; WPF's built-in Fluent theme was still experimental and lacks those controls.

### 3. Run as a standard user, elevate on demand (October 2026)

**Decided:** the manifest uses `asInvoker`. AutoClick detects games running at a higher integrity level (and `PostMessage` failures with access denied), explains the problem and offers to restart elevated, or to always run elevated.
**Why:** 1.x required administrator rights for everything. Only games that run elevated need it; Velopack also starts the app with `CreateProcess` during updates, which fails with error 740 for an exe that requires elevation. Users upgrading from 1.x keep starting elevated (with a one-time notice) so nothing breaks for them.

### 4. New settings file next to the old one (October 2026)

**Decided:** v2 writes `settings.v2.json` and never touches 1.x's `settings.json`; profiles keep the 1.x format.
**Why:** a downgrade keeps the user's 1.x configuration, and profiles stay shareable between versions.

### 5. Full Velopack packages only (October 2026)

**Decided:** `--delta None`; package id, exe name and channel fixed.
**Why:** most of the package is the self-contained runtime, so deltas save little and need the previous release at build time. Changing the package identity would orphan existing installs. Releases are uploaded as drafts and tested in Windows Sandbox (update from the previous releases with data kept) before they are published.

### 6. No WinRT projection in the package (October 2026)

**Decided:** the build drops `Microsoft.Windows.SDK.NET.dll` (24 MB) and SkiaSharp's native debug symbols (about 100 MB) from the output.
**Why:** the `windows10.0.19041` target framework (needed for the modern assets of SkiaSharp.Views.WPF) and CommunityToolkit.Mvvm pull in the WinRT projection, but no assembly of the app references it; `WinRT.Runtime.dll`, which some libraries reference, stays. The smoke test runs on the published output to catch a mistake here.
